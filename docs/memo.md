# 改善案メモ

## 1. 完了済みセッションのデータ保護 (Critical)

**現状の問題:**
現在、セッションを「完了 (completed)」した後でも、API (`UpsertCount`) を呼び出すことでカウントデータを追加・更新できてしまう。これにより、確定したはずの棚卸し結果が意図せず改ざんされるリスクがある。

**修正方針:**
`backend/internal/session/usecase.go` の `UpsertCount` メソッド内で、データの更新処理を行う前にセッションの状態を確認するロジックを追加する。

```go
// 修正イメージ (擬似コード)
func (u *Usecase) UpsertCount(ctx context.Context, sessionID, skuID int64, quantity int) error {
    // 1. セッションを取得
    session, err := u.sessionRepo.FindByID(sessionID)
    if err != nil {
        return err
    }
    
    // 2. 状態チェック
    if session.Status == "completed" {
        return fmt.Errorf("cannot update count for completed session") // 専用のエラーを返すのが望ましい
    }

    // 3. 更新処理 (既存ロジック)
    // ...
}
```

## 2. バーコード / JANコード対応 (Feature Request)

**現状の課題:**
商品名を選択してカウントを行っているため、商品数が増えると検索・選択の手間がかかる。

**改善案:**
1.  **データモデル:** `skus` テーブルに `barcode` (または `jan_code`) カラムを追加し、ユニーク制約を付与する。
2.  **API:** バーコードで商品を検索するAPI、またはカウント登録時にバーコードを直接送信できるAPIを追加する。
3.  **UI:** フロントエンドにバーコードスキャナ（またはカメラ）からの入力を受け付けるモードを追加する。

## 3. その他の気づき

*   **エラーハンドリング:** DBのユニーク制約違反などが汎用的な500エラーとして返されている箇所があるため、ユーザーへのフィードバックが分かりにくい（「その名前は既に使われています」等が出せない）。これについては別途エラーハンドリング設計の改善が必要。

## 4. 個人商店向け 運用考慮の改善案

### 4.1. 「一時保存（中断）」と「再開」の明確化

*   **課題:** 長時間の棚卸し作業で休憩を挟んだり、日をまたぐ際に、進行中のセッションが誤って操作されたり、意図しないデータ変更が発生するリスクがある。
*   **改善案 (運用):**
    *   休憩に入る際や作業を終える際に、必ずアプリを終了（またはログアウト）する。
    *   翌日再開する際は、改めてログインし、進行中のセッションを呼び出す。
*   **改善案 (システム):**
    *   UI上に明示的に「一時中断」ボタンを設ける。このボタンを押すと、システムの状態は保存され、ログアウトやトップ画面へ戻るなどの操作フローへ誘導する。
    *   再開時は、進行中のセッションを簡単に呼び出せるようにする。

### 4.2. カウント入力の履歴（監査ログ）

*   **課題:** 「この商品は本当に数えたか？」「入力ミスをしていないか？」といった不安や、後に数量が合わない場合の原因特定が難しい。
*   **改善案 (システム):**
    *   「いつ、誰が、何の商品を、何個追加/修正したか」という操作履歴を記録し、セッション詳細画面などで確認できるようにする。
    *   `count_items` テーブルに `version` や `transaction_id` のような概念を追加するか、別途 `count_audit_logs` テーブルを作成する。
*   **運用上のメリット:**
    *   誤入力や入力漏れに気づきやすくなる。
    *   最終的な棚卸し結果と差異が出た場合の原因特定が容易になる。

### 4.3. 商品の「棚卸し済み」マーク

*   **課題:** 大量の商品を扱う際、すでにカウントした商品とまだカウントしていない商品が一覧で分かりにくく、数え漏れや二重カウントの原因となる。
*   **改善案 (システム):**
    *   商品リスト（サイドバーなど）上で、その商品がセッション内で1個以上カウントされたら、アイコンや色、ラベルなどで「カウント済み」と視覚的にマークする。
    *   カウントがゼロに戻ったらマークを消す。
*   **運用上のメリット:**
    *   数え漏れを劇的に減らせる。
    *   棚卸し作業の進行状況がひと目で把握でき、作業効率が向上する。

### 4.4. バックアップ（エクスポート）の習慣化

*   **課題:** システム障害やデータ破損が発生した場合、棚卸しデータが失われるリスクがある。
*   **改善案 (運用):**
    *   棚卸しが完了したら、必ずCSVエクスポート機能を利用し、ダウンロードしたファイルをクラウドストレージ（Google Drive, Dropboxなど）や別のPCに保存することをルーティン化する。
    *   定期的にデータベース全体のバックアップを取る運用も検討する。
*   **改善案 (システム):**
    *   セッション完了時に、自動的にCSVダウンロードを促すポップアップを表示する。
    *   CSVファイル名を「棚卸し日付_セッション名.csv」のように、ルールを決めて出力する。

### 4.5. 誤入力防止のアラート

*   **課題:** 入力時に桁を間違えるなどのヒューマンエラーによる大きな数値の誤りが、在庫総額に致命的な影響を与える。
*   **改善案 (システム):**
    *   一度に非常に大きな数量（例: 100個以上）が入力された場合、「本当にこの数量でよろしいですか？」といった確認のアラートを表示する。この閾値は設定で変更可能にするとより良い。
*   **運用上のメリット:**
    *   在庫数の大きなズレを未然に防ぎ、再棚卸しの手間を省ける。
    *   入力時の注意力を高める効果も期待できる。
